Inspecting real Content Credentials

Time to leave the simulation. This chapter uses the official C2PA SDK, the Rust reference implementation compiled to WebAssembly, to read real files.

By the end of this chapter you will be able to

  • Read a real manifest store and find the active manifest, its signer, assertions and ingredients.
  • Interpret real validation results, including deliberately broken test files.
  • Explain why test files are “Valid” but not “Trusted”.

The tools

The Content Authenticity Initiative maintains open-source C2PA implementations: c2pa-rs (Rust), with bindings for JavaScript, Python, C/C++ and more, and the command-line tool c2patool. The inspector below uses @contentauth/c2pa-web, which runs c2pa-rs in a Web Worker. Everything happens in your browser, and files you drop in are not uploaded.

The SDK returns a manifest store report as JSON. It is a convenient view of the store rather than the raw JUMBF/CBOR, but every part corresponds to something you’ve learned. The links next to each field point back to the relevant chapter.

A guided tour

1. “C: a simple claim”

  • Find Signed by (issuer) and Certificate CN. That is the certificate subject information from chapter 5.
  • Find Algorithm. You’ll likely see Ps256 or Es256 (chapter 3).
  • Expand the assertions. Look for c2pa.actions and the hash assertions. Some older files use 1.x labels, such as c2pa.actions rather than c2pa.actions.v2, and claim version 1.
  • The validation state is Valid, not Trusted, and signingCredential.untrusted is listed under failures. These files were signed with the SDK’s test certificate, which isn’t on any trust list. The spec treats “untrusted” as a failure of the trust check, but the manifest still meets every requirement for Valid. That is exactly the “attacker re-signs” situation from the Tamper Lab: mathematically intact, but not anchored to a trusted root. You may also see signingCredential.ocsp.skipped, meaning no revocation check was performed.

2. “CA”, “CAI” and “CACA”: ingredients and chains

  • In CA and CAI, the active manifest lists ingredients: a parentOf, and in CAI also a componentOf. Those ingredient files had no credentials of their own, so the store holds only one manifest, and each ingredient says “unknown provenance”. The chain honestly stops there (chapter 9).
  • CACA is an edit of a file that already carried a manifest. Now the store holds two manifests: the active one (starred) and the earlier one, which the active manifest’s parentOf ingredient points to. This is the provenance graph from chapter 9, in a real file.

3. The broken files

  • E-sig: expect claimSignature.mismatch. The signature doesn’t match the claim (chapter 4). You’ll also see timeStamp.mismatch, because the time-stamp’s message imprint no longer matches the altered signature (chapter 6).
  • E-uri: expect assertion.hashedURI.mismatch. An assertion was altered after signing (chapter 7).
  • E-dat: expect assertion.dataHash.mismatch. The image bytes no longer match the hard binding.
  • A: no manifest at all. This shows how an ordinary JPEG looks: its EXIF says Canon and Lightroom, but nothing verifies that.

Compare these with the Tamper Lab table in chapter 8. The production SDK reports the same codes for the same attacks.

Try your own files

Content Credentials are increasingly common. Images to try, if you have them:

  • Photos from C2PA-capable cameras (several Leica, Sony, Nikon and Canon models) or phones with Content Credentials support.
  • Images from AI generators that attach Content Credentials. Their manifests typically record trainedAlgorithmicMedia.
  • Images exported from editing software with Content Credentials enabled.

Real-world credentials signed by certificates on the C2PA Trust List may still show as Valid here. This inspector uses the SDK’s default settings and is not configured with the official trust list, which is a reminder that trust is always a validator configuration. Public tools such as the Content Credentials “Verify” site configure trust lists for you.

For developers

The same report is available on the command line with c2patool yourfile.jpg, or with c2patool yourfile.jpg --detailed for a lower-level view closer to the actual CBOR structures. In code, the reading step this page performs is essentially: 

const c2pa = await createC2pa({ wasmSrc });
const reader = await Reader.fromBlob(c2pa, blob.type, blob);
const store = await reader.manifestStore();   // the JSON report
console.log(store.validation_state, store.active_manifest);
