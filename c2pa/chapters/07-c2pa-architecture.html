Anatomy of a C2PA manifest

A C2PA manifest is hashes and signatures arranged with care. This chapter takes one apart and puts it back together.

By the end of this chapter you will be able to

  • Name the parts of a manifest: assertions, claim, claim signature. Explain how they connect.
  • Explain hashed URIs and the chain of hashes from content to signature.
  • Describe hard bindings and soft bindings.
  • Read the main assertion types: actions, ingredients, metadata, thumbnails.
  • Explain what JUMBF, CBOR and COSE are, and where a manifest lives in a file.

The vocabulary

AssetThe content: an image, video, audio file, PDF, font…
Claim generatorThe hardware or software that creates and signs a manifest: a camera’s firmware, an editing app, an AI image service.
AssertionOne statement about the asset: “this was created by a camera”, “these edits were made”, “this is the hash of the pixels”.
ClaimThe signed summary: a list of references (with hashes) to every assertion, plus information about the claim generator.
Claim signatureThe claim generator’s digital signature over the claim, with its certificate chain and usually a time-stamp.
ManifestAssertions + claim + claim signature: one signed record of one step in the asset’s life.
Manifest storeAll the manifests for an asset (its own plus those of its ingredients), packaged together. The newest is the active manifest.

The chain of hashes

The whole design is a chain in which each link is protected by the one above it:

content bytes └─ hashed by ──▶ hard-binding assertion (c2pa.hash.data: { hash: SHA-256(content) }) assertions (each one) └─ hashed by ──▶ claim.created_assertions[]: { url, alg, hash } claim └─ signed by ──▶ claim signature (COSE_Sign1, ES256, with x5chain) signer's certificate └─ chains to ──▶ trust anchor on the validator's trust list

Change the content and the hard-binding hash breaks. Change an assertion and its hash in the claim breaks. Change the claim to fix that and the signature breaks. Re-sign with your own key and the trust anchor breaks. That chain is the core of C2PA, and chapter 8 lets you attack every link.

Assertions in detail

Each assertion has a label that says what kind it is. Labels beginning with c2pa. are defined by the C2PA specification. Other organisations use their own prefixes (CAWG uses cawg.). The most important ones are:

Actions: c2pa.actions.v2

A list of things that happened to the asset, in order. Each action has a name and optional details:

  • c2pa.created: the asset was brought into existence. It must say how, using a digitalSourceType from the IPTC vocabulary: digitalCapture (a camera or sensor), trainedAlgorithmicMedia (generated by AI), compositeWithTrainedAlgorithmicMedia, digitalCreation (made by a person in software), and others.
  • c2pa.opened: an existing asset (an ingredient) was opened to be edited.
  • c2pa.edited, c2pa.cropped, c2pa.color_adjustments, c2pa.resized, c2pa.filtered…: specific edits.
  • c2pa.placed: another asset was placed into this one (compositing).
  • c2pa.converted, c2pa.transcoded: format changes. c2pa.published: published.
  • c2pa.redacted: an assertion from an earlier manifest was removed (for example, GPS location for privacy).

An action can also record a when time, the softwareAgent that performed it, and parameters (for example, which ingredient it relates to).

Hard bindings: tying the manifest to the content

A hard binding is an assertion containing a cryptographic hash of the asset’s content. Every manifest that describes content must have exactly one. There are several kinds, because file formats differ:

  • c2pa.hash.data: a hash over the file’s bytes, with exclusion ranges. Used for JPEG, PNG and similar.
  • c2pa.hash.bmff.v3: for ISO base media (MP4, MOV, HEIF/AVIF). It hashes box structures and supports fragmented/streaming video via Merkle trees.
  • c2pa.hash.boxes: hashes named sections of box-based formats individually.
  • c2pa.hash.collection.data: for collections of files.
The chicken-and-egg problem, and exclusions

The manifest is stored inside the file, but the hard binding is a hash of the file, so the manifest can’t contain a hash of itself. The fix is to exclude the byte range where the manifest store sits from the hash. A claim generator typically writes a placeholder of the right size, computes the hash over everything else, then fills in the real manifest. A validator recomputes the hash, skipping exactly the declared exclusion ranges. (In the simulation we hash raw pixels only, so exclusions are just shown symbolically.)

Soft bindings: c2pa.soft-binding

A soft binding identifies the content in a way that survives changes such as re-compression or resizing. It might be an invisible watermark embedded in the pixels, or a perceptual fingerprint computed from them. Soft bindings can’t prove integrity, because they are designed to tolerate changes. They are a lookup key: if the manifest is stripped, the watermark or fingerprint can be used to find it again in a repository. Chapter 9 shows this in action.

Ingredients: c2pa.ingredient.v3

When an asset is made from other assets, each source is recorded as an ingredient with a relationship: parentOf (the asset being edited), componentOf (something placed into it) or inputTo (for example, an image used as a prompt for an AI model). If the ingredient had its own manifest, that manifest is copied into the manifest store and the ingredient assertion references it by hash. This is how provenance chains form (chapter 9).

Metadata, thumbnails and more

  • c2pa.metadata: a limited, specified set of descriptive metadata (for example, some EXIF camera fields) stored inside the signed manifest, so it gains the integrity that ordinary metadata lacks.
  • c2pa.thumbnail.claim / c2pa.thumbnail.ingredient: small preview images, so a viewer can show what an earlier version looked like.
  • CAWG-defined assertions such as cawg.identity and cawg.training-mining (Part IV).

The claim in detail

The claim (in 2.x, a c2pa.claim.v2) is a small structure. Its main fields are:

  • instanceID: a unique identifier for this specific version of the asset.
  • claim_generator_info: name and version of the software or hardware that made the claim.
  • signature: a reference to where the claim signature is stored.
  • created_assertions: hashed URIs to the assertions this claim generator itself created.
  • gathered_assertions: hashed URIs to assertions it collected from elsewhere and is passing along without vouching for their content. For example, an assertion supplied by the user.
  • redacted_assertions: references to assertions in ingredient manifests that have been removed.
  • alg: the default hash algorithm used.

A hashed URI is the key data structure: { url, alg, hash }. The URL says where the thing is (for example, self#jumbf=c2pa.assertions/c2pa.actions.v2, meaning “in this manifest, in the assertion store, the box labelled c2pa.actions.v2”). The hash says exactly what it must contain. A pointer that can’t be silently redirected.

The claim signature: COSE

C2PA signs claims with COSE (CBOR Object Signing and Encryption, RFC 9052), using its single-signer structure, COSE_Sign1. It has three parts:

  • A protected header, which is signed. It contains the algorithm (e.g. ES256) and the signer’s certificate chain (x5chain: leaf first, then intermediates. The root isn’t included because the validator must already have it).
  • An unprotected header, which is not signed. It holds things that may be added later, like the RFC 3161 time-stamp and stapled OCSP responses.
  • The signature. The payload (the claim) is detached: it is stored separately in the manifest rather than copied into the COSE structure.

What actually gets signed is a structure called Sig_structure: the string “Signature1”, the protected header and the claim’s bytes. That is why changing either the claim or the declared algorithm/certificates invalidates the signature. The builder above shows a simplified version of these to-be-signed bytes.

Encodings: CBOR and JUMBF

  • CBOR (Concise Binary Object Representation, RFC 8949) is like JSON but binary and compact. Claims and most assertions are CBOR. Crucially, it can be encoded deterministically, so the same data always becomes the same bytes and hashes are reproducible. (The simulation uses JSON with sorted keys for the same purpose.)
  • JUMBF (JPEG Universal Metadata Box Format, ISO/IEC 19566-5) is a container format made of labelled, nestable boxes. The manifest store is a JUMBF superbox labelled c2pa, containing one box per manifest. Each of those contains an assertion store box, a claim box and a signature box, exactly the nested picture at the bottom of the builder.

Where the manifest lives

The same JUMBF manifest store is embedded differently depending on the file format:

  • JPEG: in one or more APP11 marker segments.
  • PNG: in a caBX chunk.
  • MP4 / MOV / HEIF / AVIF: in a dedicated uuid box.
  • PDF, WebP, TIFF/DNG, MP3/WAV, fonts and others each have defined locations.
  • Sidecar or remote: the store may also live in a separate .c2pa file or on a server, referenced from the asset (for example, by a URL in its XMP metadata). This helps when embedding is impossible or the store is very large.
Key idea

Assertions say things. The claim lists them by hash. The signature vouches for the claim. The certificate says who signed. The hard binding ties it all to specific bytes. No single part can be changed without breaking another.
