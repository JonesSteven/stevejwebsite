Certificates and chains of trust

A certificate is a signed statement: “this public key belongs to this name”. Chain a few together and a handful of trusted organisations can vouch for millions of keys.

By the end of this chapter you will be able to

  • Describe what is inside an X.509 certificate.
  • Explain root, intermediate and end-entity (leaf) certificates and how a chain is validated.
  • Explain trust anchors and trust lists, including the C2PA Trust List.
  • Explain revocation and why it exists.

A certificate is a signed sentence

Recall the problem from chapter 4: a public key carries no name. The fix is to have someone you trust sign a statement that links them:

“The public key 04:a1:9c:…:3f belongs to PhotoApp Inc. Signatures it verifies may be trusted as C2PA claims signed by PhotoApp Inc. This statement is valid from 2025-01-01 to 2027-01-01.” — signed, Example Issuing CA

That signed statement is a certificate, and the signer is a Certificate Authority (CA). If you trust the CA’s public key, you can verify the CA’s signature on the certificate and believe the name–key link it states.

Notice what is, and isn’t, inside. A certificate contains only the public key, because it is meant to be shown to everyone. The matching private key never leaves PhotoApp Inc., and the CA never sees it. So when a certificate says what a key “may be used for”, it is talking about the key pair: PhotoApp’s private key may sign C2PA claims, and the public key in the certificate is what everyone else uses to verify those signatures.

Inside an X.509 certificate

Virtually all certificates on the internet, and those C2PA requires, follow the X.509 standard (RFC 5280). The important fields are:

FieldMeaning
SubjectWho the key belongs to (e.g. CN=PhotoApp Inc., O=PhotoApp, C=US).
Subject Public Key InfoThe public key itself and its algorithm (e.g. EC P-256).
IssuerThe CA that signed this certificate.
Serial numberUnique per issuer. Used for revocation.
Validity (notBefore / notAfter)The window during which the certificate is valid.
Basic ConstraintsIs this a CA (allowed to sign other certificates) or an end-entity?
Key Usage / Extended Key Usage (EKU)What the key pair may be used for: what the matching private key may sign, and so what signatures this public key may be trusted to verify. C2PA defines an EKU for claim signing; time-stamp authorities use the timeStamping EKU.
SignatureThe issuer’s signature over all the fields above.

Real certificates are encoded in a binary format (ASN.1 DER). In the demos we use a simplified JSON form, but each certificate is genuinely signed with a real ECDSA key, and validation genuinely checks those signatures.

Chains: trust that scales

One CA signing every key on Earth wouldn’t work, and if its key leaked, everything would fall. So certificates form a hierarchy:

  • A root CA has a self-signed certificate, signed by its own private key. Nobody vouches for a root. You choose to trust it. Root keys are kept offline in vaults and used rarely.
  • The root signs certificates for intermediate CAs, which do the day-to-day issuing.
  • Intermediates sign end-entity (or “leaf”) certificates for the actual signers: a camera model, an app, a service.

To check a leaf certificate, a validator walks the chain: leaf → intermediate → root. At each link it checks the signature, that names match, that the issuer is allowed to be a CA, the validity dates, and revocation status. Finally it checks that the root is one it trusts. That last step is the trust anchor.

Work through each switch and read which check fails:

  • Untrust the root: every signature still verifies, but the chain ends somewhere you have no reason to believe. Mathematics can’t create trust. It can only carry it.
  • Tamper with the leaf’s name: the intermediate’s signature over the leaf no longer matches.
  • Rogue root: an attacker can make a perfect chain to their own root with any name on it. Only the trust store stops this.
  • Non-CA issuer: a valid leaf certificate (say, for a website) can’t be used to vouch for other keys.
  • Move the date: certificates are only valid within their window. (The next chapter shows how signatures can outlive it.)

Trust anchors and trust lists

Every validator ships with, or is configured with, a trust store: the set of root certificates it trusts. Your web browser trusts roughly 150 roots chosen by Apple, Google, Microsoft or Mozilla. That’s why your browser accepts https:// certificates from sites it has never seen.

C2PA validators work the same way. Since C2PA 2.0, the specification defines a default C2PA Trust List of CAs that issue certificates to conforming hardware and software products, administered through the C2PA conformance programme. A validator may also be configured with additional trust anchors, for example a newsroom trusting its own internal CA.

Key idea

Cryptography answers “did this key sign this?”. Certificates answer “whose key is this, according to whom?”. The trust store answers “do I believe the ‘according to whom’?”. That last question is a policy decision, not a mathematical one, and different validators can legitimately answer it differently.

Revocation: taking it back

What if a private key is stolen, or a certificate was issued by mistake, before its expiry date? The CA revokes it and publishes that fact, so validators can check:

  • CRL (Certificate Revocation List): a signed list of revoked serial numbers, published periodically.
  • OCSP (Online Certificate Status Protocol): a signed real-time answer to “is serial X still good?”. C2PA allows OCSP responses to be stored (“stapled”) inside the manifest, so validation still works offline later.

Revocation raises a puzzle. If a camera’s key is revoked in June 2025, what about the honest photos it signed in 2024? They shouldn’t suddenly become untrustworthy, but we need proof they were signed before the compromise. That proof is a trusted time-stamp, the topic of the next chapter.

C2PA specifics

The C2PA specification requires claim signers to use X.509 certificates. It defines certificate profile requirements (key usage, EKU, algorithms) and validation outcomes such as signingCredential.trusted, signingCredential.untrusted, signingCredential.invalid and signingCredential.ocsp.revoked. You’ll see these codes produced in the Tamper Lab and by the real SDK in chapter 10.
