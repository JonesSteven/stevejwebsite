Hash functions: digital fingerprints

Hashing is the first building block. A hash turns data of any size into a short fingerprint that changes completely if even one bit of the data changes.

By the end of this chapter you will be able to

  • Explain what a cryptographic hash function is and what SHA-256 outputs.
  • Name and explain determinism, the avalanche effect, preimage resistance and collision resistance.
  • Explain why a hash can stand in for a large file, and why that matters for signatures.

First: everything is bytes

Computers store everything, including text, photos, video and this web page, as sequences of bytes. A byte is 8 bits (0s and 1s), so it can hold a number from 0 to 255. The letter “A” is stored as byte 65. A pixel in a photo is typically three bytes: red, green and blue intensities. A 12-megapixel photo is roughly 36 million bytes before compression.

We often write bytes in hexadecimal (base 16), using digits 0–9 and a–f. One hex digit represents 4 bits, so one byte is exactly two hex digits: 65 becomes 41 and 255 becomes ff. You’ll see a lot of hex in this course. Whenever you see a long string like 9f86d081…, it’s just bytes written compactly.

What a hash function does

A hash function takes an input of any length and produces an output of a fixed length, called the hash or digest. C2PA, like most modern systems, uses SHA-256 (Secure Hash Algorithm, 256-bit output). Whether you feed it one letter or a 4 GB video, you get back exactly 256 bits: 32 bytes, or 64 hex digits.

Think of a hash as a fingerprint for data. It is much smaller than the thing it identifies, the same thing always gives the same fingerprint, and you can’t rebuild the person from the fingerprint.

The four properties that matter

Not every function that squeezes data into a fixed size is useful for security. A cryptographic hash function must have all of these properties:

1. Deterministic

The same input always gives the same output, on any computer, forever. This is what lets someone else re-compute a hash and compare it with yours. In the demo, make the two inputs identical and watch the hashes match.

2. The avalanche effect

A tiny change to the input (one character, one bit) produces an output that looks completely unrelated. About half of the 256 output bits flip, in an unpredictable pattern. In the demo, the two default inputs differ only by a full stop, yet the bit grid lights up across the board. This means a hash gives no clue about how similar two inputs are. It only tells you whether they are exactly equal.

3. Preimage resistance (one-way)

Given a hash, it must be infeasible to find any input that produces it. There is no “reverse SHA-256” button. The only strategy is to guess inputs, hash them and compare, and the space of possible outputs is astronomically large: 2256 ≈ 1077, close to the number of atoms in the observable universe. The demo below lets you feel how quickly guessing becomes hopeless, even when you only need to match a few hex digits.

Each extra hex digit you require makes the search 16 times longer on average. Matching all 64 digits would take every computer on Earth far longer than the age of the universe. (Bitcoin “mining” is this same puzzle, deliberately tuned to be hard.)

4. Collision resistance

It must be infeasible to find two different inputs that produce the same hash. Collisions must exist mathematically, since there are infinitely many inputs and only 2256 outputs. But nobody can find one. Because of the “birthday paradox”, finding a collision takes about 2128 attempts rather than 2256. That is still far beyond reach.

History lesson

Older hash functions lost these properties. Practical collisions were found for MD5 (2004) and SHA-1 (2017), and both are now forbidden in security systems. This is why specifications like C2PA name the exact algorithms allowed (SHA-256, SHA-384, SHA-512) and record which one was used next to each hash, so systems can move to stronger algorithms later.

Hashing a whole file

Files are bytes too, so they can be hashed. Choose any file below: a photo, a PDF, anything. Then flip a single bit in it.

Try verifying it yourself. On macOS or Linux, run shasum -a 256 yourfile.jpg in a terminal. On Windows, run certutil -hashfile yourfile.jpg SHA256. You’ll get the same 64 hex digits.

Why this matters for provenance

Hashes give us two superpowers that C2PA uses everywhere:

  1. Tamper evidence. If I record the hash of a photo today and you hash it tomorrow, matching hashes mean the bytes are identical. A different hash means something changed, even one pixel. (Hashes can’t tell you what changed. They can only tell you whether anything did.)
  2. Compact stand-ins. Instead of handling a 30 MB photo, you can handle its 32-byte hash, and thanks to collision resistance the hash is as good as the photo for checking identity. This matters because, as you’ll see, signatures are always computed over hashes, never directly over huge files.

C2PA chains hashes together. The manifest contains a hash of the content. A signed list contains the hashes of each piece of the manifest. Tamper with anything and some hash in the chain stops matching.

Key idea

A hash proves sameness but not origin. Anyone can compute a hash, including an attacker who modifies a file and then hashes the modified version. To make a hash trustworthy, we need a way to show that a specific party vouched for it. That is the job of public-key cryptography and signatures, in the next two chapters.
