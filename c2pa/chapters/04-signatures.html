Digital signatures

Combine a hash with a private key and you get a digital signature: a small piece of data that proves a particular key holder approved particular bytes, and that those bytes haven’t changed since.

By the end of this chapter you will be able to

  • Describe the sign and verify procedures step by step.
  • Explain why signatures are computed over hashes.
  • State precisely what a valid signature does, and does not, prove.
  • Explain the “which public key?” problem that motivates certificates.

The recipe

Every modern signature scheme, including the ECDSA used by C2PA, follows the same shape:

Signing (by the key owner)
  1. Take the message bytes M.
  2. Compute h = SHA-256(M).
  3. Combine h with the private key using the signing algorithm → signature S.
  4. Publish M and S together.
Verifying (by anyone)
  1. Receive M′ and S (M′ may or may not equal M).
  2. Compute h′ = SHA-256(M′).
  3. Run the verification algorithm on h′, S and the public key.
  4. It outputs valid or invalid. Nothing in between.

Why hash first? Signature mathematics works on numbers of a fixed size (256 bits for P-256). Hashing turns a message of any size into exactly that size, and thanks to collision resistance, signing the hash is as good as signing the message. Change any bit of M and h′ differs from h, so the signature no longer fits.

In the toy RSA demo in chapter 3, “signing” was s = md mod n and verifying was checking se mod n = m. ECDSA’s equations are different, but the logic is the same. Only the private key can produce a value that passes a check anyone can run with the public key.

Try it

Alice and Mallory each have a freshly generated P-256 key pair. Alice signs a message. On the right, you are the verifier. Edit the message, edit the signature, check against the wrong public key, or let Mallory try to forge.

Experiments worth doing:

  • Add a single space to the received message. It becomes invalid, because the hash changed.
  • Change one hex digit of the signature. Invalid.
  • Switch the public key to Mallory’s. Invalid: this signature was not made by her key.
  • Click “Let Mallory try to forge”. She signs a modified message with her key, but you are checking against Alice’s key, so it fails.
  • Click “Sign” twice. ECDSA signatures include a fresh random value (the nonce k), so each signature differs, and all of them verify. (Ed25519 derives the nonce deterministically instead; both approaches are secure.)
Real-world failure: nonce reuse

If an ECDSA signer ever uses the same nonce k for two different messages, anyone can compute their private key from the two signatures with simple algebra. This happened to Sony’s PlayStation 3 code-signing key in 2010. Good cryptographic libraries make this mistake impossible, which is one reason never to implement signatures yourself.

What a valid signature proves

When verification succeeds, you know exactly two things:

  1. Integrity: the bytes you have are bit-for-bit identical to the bytes that were signed.
  2. Key possession: the signature was produced by someone holding the private key that matches the public key you used.

Hidden inside the second point is a consequence called non-repudiation. If only Alice has her private key, she can’t later convincingly deny signing. This is exactly what symmetric keys couldn’t give us.

What it does not prove

  • Not truth. Alice can sign “the moon is made of cheese”. The signature proves Alice’s key signed it, not that it’s correct.
  • Not intent or circumstance. If Alice’s key was stolen, the thief’s signatures verify perfectly.
  • Not identity, on its own. This is the big one. Verification tells you a signature matches a public key. It says nothing about whose key that is.

The “which public key?” problem

Suppose a photo arrives with a signature and a public key attached, and a note saying “this is Reuters’ public key”. The signature verifies. Have you learned that Reuters signed it?

No. Mallory can generate her own key pair, sign anything, attach her public key, and label it “Reuters”. The maths will check out perfectly. A bare public key is just a big number with no name attached.

You could keep a list of every legitimate public key in the world, but there are billions of devices and apps, and keys change. What we need is a scalable way for a few parties you already trust to vouch for other people’s keys. That is a certificate, and it is the subject of the next chapter.

Key idea

Signature = hash + private key. Verification = hash + public key + signature → yes/no. A valid signature binds bytes to a key. Binding a key to a name takes a certificate.
