Secret keys, key pairs and the trapdoor

Public-key cryptography is one of the great inventions of the 20th century. It lets you prove something to people you have never met, without sharing any secret with them.

By the end of this chapter you will be able to

  • Explain symmetric cryptography and its key-distribution problem.
  • Explain what a key pair is and why the private key must stay private.
  • Work through RSA key generation, encryption and signing with small numbers.
  • Describe, conceptually, how elliptic-curve keys (used by C2PA’s ES256) work.
  • Recognise keys in the formats you’ll meet in the wild (JWK, PEM).

Symmetric cryptography: one shared secret

The oldest kind of cryptography is symmetric: both sides use the same secret key. Caesar shifting letters by three, wartime Enigma machines and today’s AES all work this way. Alice locks the message with the key, and Bob unlocks it with the same key.

Symmetric ciphers are fast and strong, but they have two problems that matter to us:

  1. Key distribution. Alice and Bob must agree on the secret before they can communicate securely. Doing that over an insecure channel is the very problem we were trying to solve.
  2. No proof of authorship. If Alice and Bob share a key, either of them could have produced any message. Bob can’t prove to a third party that Alice wrote something, because he could have written it himself. For provenance, where the whole world must be able to check who vouched for a photo, this is fatal.

The asymmetric idea: two keys, one lock

In 1976 Whitfield Diffie and Martin Hellman published a radical idea, and in 1977 Rivest, Shamir and Adleman (RSA) gave a practical construction. (GCHQ researchers had found it secretly a few years earlier.) The idea: generate two different keys that are mathematically linked.

  • A private key, which you keep secret. Nobody else ever sees it.
  • A public key, which you publish to the whole world.

What one key does, only the other can undo or check. That gives two uses:

UseLock withUnlock / check withResult
Encryptionrecipient’s public keyrecipient’s private keyOnly the recipient can read it.
Signingsigner’s private keysigner’s public keyAnyone can check it came from the signer.

C2PA uses only the second use, signing. There is no encryption in C2PA: manifests are meant to be read by everyone. The point is to make them unforgeable, not secret.

A useful picture for signing: a wax seal. Only you own the signet ring (private key), but everyone knows what your seal looks like (public key) and can check an impression against it. Unlike wax, a digital seal is also bound to the exact content it seals.

How can such keys exist? Trapdoor functions

The trick is a trapdoor one-way function: an operation that is easy to perform, practically impossible to reverse, unless you know a secret shortcut (the trapdoor). The public key lets anyone do the easy direction. The private key is the trapdoor.

RSA’s trapdoor is multiplying primes vs. factoring:

  • Multiplying two primes is easy. 61 × 53 = 3233 takes moments by hand, and a computer can multiply two 300-digit primes in microseconds.
  • Going backwards is hard. Given only 3233, which two primes made it? For small numbers you can try them all. For a 617-digit number, every known classical method would run for longer than the age of the universe.

A tiny bit of modular arithmetic

RSA works with modular arithmetic, or “clock arithmetic”. On a 12-hour clock, 9 o’clock plus 5 hours is 2 o’clock: you wrap around. We write that as (9 + 5) mod 12 = 2. “mod n” just means “take the remainder after dividing by n”. So 17 mod 5 = 2, and 34 mod 7 = 81 mod 7 = 4.

The key fact RSA relies on: there are numbers e and d such that raising to the power e and then to the power d (mod n) gets you back where you started. In other words, (me)d mod n = m. Finding d from e requires knowing φ(n) = (p−1)(q−1), and computing that requires the prime factors p and q. That is the trapdoor.

Textbook RSA is not real-world RSA

Real systems never apply RSA directly to a message like this. They first hash the message (chapter 2) and use a padding scheme with randomness. C2PA permits RSASSA-PSS (“PS256/PS384/PS512”) with keys of at least 2048 bits. The underlying mathematics, though, is exactly what you just did.

Elliptic curves: smaller keys, same strength

RSA keys must be large (2048–4096 bits) to be safe. Elliptic-curve cryptography (ECC) gives equivalent security with much smaller keys (256 bits), so it is faster and lighter. It’s the default in most modern systems, including most C2PA implementations, which typically sign with ES256: ECDSA on the curve P-256 with SHA-256.

Here is the idea, without the algebra:

  • An elliptic curve is a set of points (x, y) satisfying an equation like y² = x³ + ax + b, computed modulo a large prime. Plotted, it’s a scatter of points, not a smooth curve.
  • There is a way to “add” two points on the curve to get a third point on the curve. Adding a point to itself repeatedly is called scalar multiplication: d × G = G + G + … + G (d times), where G is a fixed, publicly known “generator” point.
  • Computing Q = d × G is fast, even for d around 2256, using a doubling trick, much like the square-and-multiply in the RSA demo.
  • Going backwards, finding d given only Q and G, is the elliptic-curve discrete logarithm problem, and no efficient method is known.

So an elliptic-curve key pair is simply:

private key d = a random 256-bit number public key Q = d × G (a point: two 256-bit coordinates x, y)

Ed25519 is another popular curve-based scheme (EdDSA on Curve25519), also permitted by C2PA. The full list of signature algorithms allowed by the C2PA specification is: ES256, ES384, ES512 (ECDSA), PS256, PS384, PS512 (RSA-PSS), and Ed25519.

Things to notice:

  • The private key is just a number, d, encoded in base64url. Everything else is derived from it.
  • The public key is the point (x, y). Formats like JWK (JSON Web Key) and PEM (base64 text between “BEGIN/END” lines) are different wrappings of the same numbers.
  • Generate a few. Each one is different, because private keys must come from a high-quality random source. A predictable private key is a broken private key.

Keeping private keys private

Everything in this course depends on one assumption: only the owner can use their private key. In practice:

  • Cameras keep signing keys in secure hardware (a secure element or trusted execution environment) that can sign but will never reveal the key.
  • Services keep keys in Hardware Security Modules (HSMs) or cloud key-management services.
  • If a private key leaks, anyone can sign as its owner. Chapter 5 covers how the world is told to stop trusting a leaked key (revocation), and chapter 6 how earlier signatures can remain trustworthy anyway.

The C2PA specification has explicit requirements for how claim generators must protect their signing keys, because a stolen camera key would let an attacker sign fake “camera captures”.

A note on quantum computers

A large, fault-tolerant quantum computer could break both RSA and elliptic-curve cryptography using Shor’s algorithm. None exists today, but standards bodies have published post-quantum signature algorithms (for example ML-DSA). Specifications like C2PA name their algorithms explicitly partly so they can add new ones over time.
